本文件记录本项目的**已确认决策**。它是对话结论的唯一持久化位置：新会话、新 Agent 开工前必读，
不要依赖聊天记录或某一侧的记忆文件来判断"这件事定没定过"。

`AGENTS.md` 是入口，`docs/STATUS.md` 是当前状态快照，本文件回答"为什么这样定、哪些方案被否掉"。

状态只能由用户确认或可验证的提交/验证结果推进。已废弃条目不删，避免后来者重复踩坑。

## D01 · 项目定位与职责边界

- 状态：已确认
- 依据：提交 `4ce2ca8`；`AGENTS.md`「这个项目在做什么」

**背景**：Claude Code 版本比第三方网关新，会发出上游不认识的请求字段，需要一层本地兼容。

**结论**：只做"转发前改写请求体"。不做鉴权、不做 provider 管理、不做用量统计、不做故障转移；
不解析、不缓存、不改写响应体；不按端点做特殊处理，全部走兜底转发。

**理由**：这些职责属于 cc-switch。吸进来会与它的版本演进互相牵连，失去"随时可摘掉"的属性。

**未选**：把网关做成全能代理（含鉴权、限流、计费）。

**影响文件**：`crates/gateway-core/src/forward.rs`、`server.rs`、`AGENTS.md`。

## D02 · 兼容规则采用语义等价降级，不是丢弃信息

- 状态：已确认
- 依据：提交 `4ce2ca8`；`AGENTS.md`「历史背景」

**背景**：两个原始故障分别是 `tool_reference` 导致 500（且历史重放使会话永久卡死），
以及 `thinking:{type:"disabled"}` 导致 400（LiteLLM 未配 `model_info.thinking_disable_mode`）。

**结论**：
- `thinking.type == "disabled"` → 删除整个 `thinking` 字段。`enabled` 一律不动。
- `tool_result` 里的 `tool_reference` → 合并成一个 `text` 块，内容是"已加载工具: ..."。

**理由**：`tool_reference` 原本只表示"以下工具已加载"；删除 `disabled` 等价于"不声明 thinking"。
两者都未改变上游收到的语义。实测删除后上游无 thinking 块、无 400/500。

**未选**：把 `disabled` 翻译成 `reasoning_effort` 的某个取值。实测 `none` / `disable` / `minimal`
全被上游 400，`low` / `medium` / `high` 都是"开启思考"档，翻译只会把"关"变成"开"。

**影响文件**：`src/rewrite/thinking_disable.rs`、`src/rewrite/tool_reference.rs`、`docs/rules.md`。

## D03 · 独立网关，不 fork cc-switch

- 状态：已确认
- 依据：`AGENTS.md`「历史背景」；工作区日志 2026-10-23

**背景**：cc-switch 的 `src-tauri/src/proxy/` 已有一组请求改写模块，
`thinking_rectifier.rs::normalize_thinking_type` 是空操作，是天然插入点。

**结论**：做独立网关，不在 cc-switch 源码上加开关。

**理由**：cc-switch 的 `proxy/mod.rs` 是固定模块清单、没有插件注册表，"外挂"物理上做不到；
作者显式写了"请求前不做 thinking type 主动改写"，主动改写违背其设计意图，提 PR 大概率被拒。
独立项目换来规则可无限扩展、不与上游版本绑死。

**代价**：多一个进程、一个端口；需要自行维护。

**未选**：fork cc-switch 长期维护分支（每次发版要 rebase、自建版本无签名）。

## D04 · 转发层五条硬约束

- 状态：已确认
- 依据：`docs/architecture.md`「关键设计决策」；`AGENTS.md`「代码规则」

**结论**：
1. 响应流式透传，`Body::from_stream`，不缓冲（回环实测 SSE 间隔 306ms 与上游一致，字节级 sha256 相同）。
2. 强制 `accept-encoding: identity`，避免流式转发时 `content-length` 与 `content-encoding` 对不上。
3. `use_system_proxy` 默认 false、构建 client 时 `.no_proxy()`。环境里的 `HTTP_PROXY` 会把本地请求
   劫持走，并使请求行变成 absolute-form。
4. `max_body_bytes` 默认 64MiB，超限返回 413，不把进程拖死。
5. **绝不记录请求体或响应体**，也不加 `log_bodies` 开关。请求体是完整对话内容与源码副本。

**请求侧边界**：chunked 上传会被收拢成完整请求（JSON 改写必须拿到完整文档）。Claude Code 的请求
本就是一次性完整 JSON POST，只有响应是 SSE，因此无实际影响。将来若需请求侧流式，走
"非 JSON 直接透传 stream"的旁路，不改主路径。

**影响文件**：`forward.rs`、`logging.rs`、`config.rs`、`docs/architecture.md`。

## D05 · 配置与路径解析不依赖进程工作目录

- 状态：已确认
- 依据：`config.rs::discover` / `resolve_path`；`AGENTS.md`「配置与路径解析」

**结论**：查找顺序为 `CLAUDE_GATEWAY_CONFIG` → 当前工作目录 → 可执行文件真实目录 →
`~/.config/claude-gateway/config.toml`；相对路径以**实际加载的配置文件所在目录**为基准。

**理由**：二进制软链成全局命令后，若以 CWD 为基准，日志会散落在每个启动目录，
且配置会静默回落到内置默认值（只有一条 WARN，极易漏看）。

**平台坑**：macOS 的 `current_exe()` 不解析软链接，必须再 `canonicalize()` 一次。
`[[bin]] name = "claude-gateway"` 推导出的 crate 名是 `claude_gateway`，
不是包名 `gateway_cli`；默认日志过滤器要同时列 `gateway_core` 与 `claude_gateway`，
否则症状是"进程在跑但一条日志都没有"（已由测试锁定）。

## D06 · 日志与流级观测

- 状态：已确认
- 依据：工作区日志 2026-11-03；提交 `02c48d6`

**结论**：
- 每个转发请求一条访问日志（`status` / `elapsed_ms` / `upstream_ms` / `rewritten`），
  `upstream_ms` 只到响应头，即 TTFB，不含流式 body 时长。
- `stream_observer` 区分四种流结束：正常完成（debug）、上游提前结束（warn）、
  上游连接出错（warn）、客户端提前断开（debug）。
- 控制面 `/_gateway/*` 与 `/_panel/*` 不产生访问日志。
- 日志按天轮转，本地时间 `YYYY-MM-DD HH:mm:ss.SSS`。

**背景**：`API Error: Server error mid-response` 排障时发现，流中途断掉在访问日志里仍是
`status=200`，无法区分责任方。补上流级日志后才能给出证据。

**已验证结论**：2026-11-03 的断流集中在上游（cc-switch 记录"首包 369 字节后连接关闭"），
网关当日 5078 请求仅 2 条 500、未重启；不经过网关的直连链路也有同类中断。

## D07 · 控制台默认只读，`[rules.*]` 段可写

- 状态：**已修订（2026-11-05 21:00）**
- 依据：提交 `e6174ec`、`02c48d6`；`AGENTS.md`「目录职责」；本轮用户要求「增加规则可配置」

**结论（修正后）**：`gateway_core::panel` 的 `*_snapshot()` 仍是唯一取数入口，HTTP 路由
（`/_panel/api/*`）与 Tauri IPC 命令都调它。控制面**只放开 `[rules.*]` 段的写入**：
规则开关与参数改完立即生效，`保存` 时用 `toml_edit` 就地写回 `config.toml`。
端口、上游、日志级别等其余配置仍只读，改它们仍编辑文件后重启。

**写操作的三条硬约束**：

1. **只改规则段**。端口与上游改了本来也无法热生效（要重建 listener 和 client），
   混在一起会让「什么能热改」变模糊。
2. **落盘用 `toml_edit` 就地修改**，不用序列化重写，否则注释与段落顺序全丢。
3. **写前备份 `config.toml.bak`，失败不改内存态**。界面必须区分「已生效未落盘」与
   「已保存」，用 `rules_dirty` 表示。

**理由**：app 内嵌网关，「改完重启」等于重启 app 并断流，体验不可接受；
而规则开关是最需要试错的操作（关掉看上游是否还报错）。其余配置低频且改动代价明确，
保持只读更能避免「面板改了、文件没改、重启就丢」。

**控制面路径前缀**：`/_gateway/*`（脚本）与 `/_panel/*`（人）用下划线前缀，是为了与上游
`/v1/*` 路径空间隔离。这是约定不是保证；曾讨论过拆独立端口，结论见 D09。

## D08 · workspace 三 crate 结构

- 状态：已确认
- 依据：提交 `48b8354`、`239e890`、`e01ac80`

**结论**：`gateway-core`（lib，全部业务实现，不依赖任何 GUI 框架）、
`gateway-cli`（bin，入口装配）、`gateway-app`（bin，Tauri 桌面端）。
依赖方向单向，core 不知道 Tauri 存在。

**理由**：core 必须始终能被测试、被 headless 复用；桌面端只是并列的另一个入口 crate。
依赖版本集中在 `workspace.dependencies`，避免多 crate 版本漂移。

**验证**：拆分后 `cargo test --workspace` 34 通过，`clippy -D warnings` 0 警告，
新二进制在 15781 实测 health、转发、`/_panel`、改写命中计数均正常。

## D09 · 桌面端进程模型：内嵌单进程，不做进程编排

- 状态：已确认（用户拍板）
- 依据：工作区日志 2026-11-03「方案结论（用户确认）」；提交 `02c48d6`

**结论**：网关内嵌在 Tauri 同一进程。关闭窗口只销毁 WebView（改为隐藏），托盘常驻，
转发不中断；不做自动接管、不做双形态连接；自启交给系统登录项，不自己写守护。

**理由**：「app 托管子进程」需要自己维护 spawn 失败、端口竞态、健康轮询、崩溃退避、
SIGTERM→SIGKILL、孤儿进程接管等边界，且控制面 HTTP 会把日志暴露给本机任意进程。
内嵌后这些隐患逐个消失，前端改走 `invoke` 直读 `Arc<Telemetry>`，零 IPC、零编排。

**代价**：不能 headless；app 崩则转发断（靠系统拉起缓解）；改网关代码要重启整个 app。
CLI target 保留，用于将来需要 headless 的场景。两者绑同一端口、互斥，谁先起谁占。

**已废弃**：
- app 托管子进程（七类编排边界，见上）
- 内核外挂 + HTTP 控制面（CORS、端口暴露、两份配置归属）
- 手写 launchd plist 常驻（曾未经确认写入，已删除，从未加载）

## D11 · 数据层：TanStack Query + Tauri event

- 状态：已确认（2026-11-05，用户拍板）

**结论**：TanStack Query 管轮询、暂停、错误态与去重；Rust 侧定时 `emit` 遥测事件，
前端 `listen` 接收。不通过 HTTP/SSE 拉控制面数据。

**理由**：内嵌后同进程，事件推送比 2 秒轮询跟手，没有 HTTP 开销，也不需要给网关加 CORS。

**未选**：保留手写 hook + 2s 轮询（实时性一般）；仅 event 无轮询（首次快照、暂停恢复要单独处理）。

## D15 · 产品定位与一级信息架构

- 状态：**待确认**，不得据此动手
- 提出：2026-11-05

**术语说明（16:06 用户追问"你说的产品定位是啥"后补充）**：
"产品定位"用大白话就是**这个软件主要给谁用、帮他办成哪一件事**。
它决定的不是颜色和技术栈，而是打开后第一眼看到什么、能点什么。
网关只有一份数据（请求 / 流事件 / 日志 / 规则命中），同一份数据可以做成三种东西：

| 给谁用 | 打开后干什么 | 界面主角 | 因此要写的东西 |
| --- | --- | --- | --- |
| 排查单次请求报错的开发者 | 点一条请求，看被改了什么、上游为什么断 | 单条请求 | 请求详情、改写 diff、时序 |
| 关心整体稳定性的人 | 看趋势、成功率、P95、告警 | 时间与指标 | 时间序列聚合、告警、留存 |
| 长期维护上游兼容的人 | 启停 / 编辑 / 回放规则，低成本补新规则 | 规则 | 规则配置化、版本、回放 |

**待澄清的歧义**：用户最初说"太难看、像小工具、要商业化产品的角度"，
实现方一路推演成"换目标用户、做多页面产品"，但用户要的可能只是
**视觉与完成度像成熟商业软件**（留白、排版、品牌感、空态、引导），功能仍是自用控制台。
- 若是视觉质感 → 不必选 P1/P2/P3，只需定界面骨架与视觉规范，范围小得多
- 若是真做成面向他人的产品 → 才需要选定位，并连带确认目标用户与功能面

此歧义未澄清前，D15 与 D19 第 1 项都不得推进，实现方不得替用户判断。

商业化角度先定产品定位，再定 UI 框架与风格。三个候选（界面骨架预览见当轮对话）：

| 定位 | 商业参照 | 目标用户 | 一等对象 | 界面骨架 |
| --- | --- | --- | --- | --- |
| P1 本地 AI 网关调试器 | Proxyman、Charles、TablePlus、Postman | 接第三方/自建网关的开发者 | 单条请求 | 三栏：源列表 / 请求流 / 详情检视器（改写 diff、时序、原始 body） |
| P2 LLM 网关可观测平台 | Helicone、Langfuse、Portkey、Sentry | 要看用量、稳定性、上游健康的人或小团队 | 指标与时间 | 品牌栏 + 多页面导航 + 趋势图 + 告警 + 详情页 |
| P3 兼容规则工作台 | Linear、Vercel、Stripe Dashboard | 长期维护多套上游兼容规则的人 | 规则 | 规则作为一等对象：列表、开关、版本、改写预览与回放、发布 |

**待确认后补充**：选哪套（或哪两套混搭）、目标用户与核心场景、UI 框架组合、
页面清单与路由、配色与排版 token、状态设计、对 `telemetry.rs` 数据模型的新增要求
（趋势聚合、请求详情留存、规则版本等）、阶段划分与验收标准。

**注意边界**：这三个定位都会显著扩大功能面。P2 需要时间序列聚合与告警，
P3 需要规则配置化、版本与回放（此前讨论过的"有价值能力"），
P1 需要请求详情留存。选定后必须同步评估对 D01「职责单一」边界的影响，
不能悄悄把网关变成全能代理。

### Mac 平台参照（2026-11-05 补充选型依据）

**Apple HIG 原则**：用语义色 / 系统色（`labelColor`、`secondaryLabelColor`、
`separatorColor`、`windowBackgroundColor`、`controlAccentColor`），尊重用户选的强调色与深浅模式；
颜色不能是唯一的信息通道；次要文字靠不透明度分层而非随意挑浅灰。

**共性规律**：

1. 不用纯黑纯白：深色用 `#1C1C1E` 系，浅色文字 `#1D1D1F`
2. 中性阶至少五级，层级靠明度不靠边框
3. 强调色面积 ≤10%，只给主按钮、选中态、开关、图表线
4. 语义色深浅各一套，且必须配文字或形状
5. 侧栏用半透明材质（vibrancy）做层级而非描边——这是 Mac 味与 Web 味最大的分界

**代表软件**：系统设置 / Finder（原生中性 + 系统 accent）、Xcode Dark 与 Proxyman
（石墨深色，方法与状态码才上色）、Things 3（白底，分类小圆点是唯一彩色）、
Craft（暖米白 + 赤陶）、Linear Dark（明度分层 + 单一电光蓝）。
色值为目测近似，正式采用前需按实际取色校准。

**据此重新评估 D16 候选**：

| 方案 | 按 Mac 标准 |
| --- | --- |
| A 深夜石墨 | 最贴近 Xcode / Proxyman / Linear 的专业深色工具，加分；但要补"跟随系统深浅与 accent"才算原生 |
| B 品牌靛紫铺满顶栏侧栏 | **不符合 Mac 规律**，那是 Web SaaS 做法。上一轮把"识别度最高"当优点，按此标准应扣分 |
| C 暖米白 + 赤陶 | 符合 Craft / Bear 类内容工具；但网关控制台数据密集，暖底长时间看日志偏累 |
| D 冷石板蓝 | 浅色里最稳，但偏 Web 控制台，Mac 原生感弱 |

**分析倾向**：以 A 为骨架，叠加 Mac 语义色机制（中性阶为主、跟随系统、强调色小面积、
语义色对应日志级别）。这只是依据推导出的倾向，**未获用户确认，D16 仍为待确认**。

## D20 · 日志能力的完整边界

- 状态：已确认（2026-11-05，用户选择「全量」）
- 相关：D04（不记请求体与响应体）

**背景**：此前只有内存环形缓冲 1000 行，界面也只接了这一个来源。后端其实已经有落盘轮转、
文件列表与文件尾部读取三个接口，但没有 IPC 出口，桌面端看不到历史；改日志级别要重启；
访问日志、改写日志、流事件之间没有任何字段能把它们对上。

**结论**：日志分两层，职责不同——

1. **内存缓冲**（1000 行）：服务「刚才发生了什么」，进程重启即清空。
2. **落盘日志**（按本地日期轮转、保留 `retain_days` 个文件）：服务「昨天那个请求怎么了」，可向上翻页。

**本次接入的范围**：

- 双源浏览：内存 / 落盘文件切换，按日选文件，默认选最新一天。
- 文件分页：`before` 游标向上翻，返回 `total` / `start` / `end` / `has_more`。
  实现是两遍顺序读，内存占用只与 `limit` 有关，不再因为文件超过 16MB 就拒绝预览。
- 打开日志目录、复制当前视图、导出当前视图为文件（导出文件名做白名单清洗，防路径穿越）。
- 日志级别运行期热切换：走 `tracing_subscriber::reload`，改完立即生效。
  （2026-11-06 修订：改为同步写回 `config.toml` 的 `[log].level`，重启后保持；见 D21）
- 请求关联 ID：6 位十六进制短串，由访问日志中间件生成，经 request extensions 传给转发层，
  访问日志、改写日志、流事件、控制台请求行共用同一个 `rid`。

**仍然不做**：不记录请求体与响应体（理由同 D04）。导出的是界面当前已显示的行，
不会顺带去读没显示的内容。

**理由**：日志的价值在「能对上号」。没有 rid 时，排查 `Server error mid-response`
只能靠时间戳猜是谁断的；没有落盘浏览时，重启后现场就没了；不能热改级别时，
为了看一眼 debug 得重启网关，等于把正在跑的对话打断。

**边界**：级别热切换只影响日志多少，不影响转发行为；不做日志聚合、全文索引、远程上报。

## D21 · 配置与日志固定到平台目录，界面改动自动落盘

- 状态：已确认（2026-11-06，用户提出并拍板）
- 相关：D20（日志能力）、D04（不记请求体）

**背景**：配置原来按「环境变量 → 工作目录 → 可执行文件目录 → `~/.config`」查找，
从哪个目录启动就用哪份配置；日志目录默认 `./logs`，跟着项目根跑。
换工作目录、软链成全局命令、或从 `.app` 启动（cwd 是 `/`）时，
配置和日志会落到不同地方。另外 `tracing_appender` 的 DAILY 按 UTC 切分，
北京时间 0:00–8:00 的日志会写进前一天的文件，和日志行里的本地时间戳对不上。

**结论**：

### 1. 固定目录

| 平台 | 配置 | 日志 |
| --- | --- | --- |
| macOS | `~/.config/claude-gateway/config.toml` | `~/Library/Logs/claude-gateway/` |
| Linux | `$XDG_CONFIG_HOME/claude-gateway/config.toml` | `$XDG_STATE_HOME/claude-gateway/logs/` |
| Windows | `%APPDATA%\claude-gateway\config.toml` | `%LOCALAPPDATA%\claude-gateway\logs\` |

macOS 的配置选 `~/.config` 而不是 `Application Support`：本项目有 CLI 入口，
配置要能进 dotfiles、能在终端里直接改。日志选 `Library/Logs`：Console.app 能直接看到，
排查时不用记隐藏路径。

`CLAUDE_GATEWAY_CONFIG` 仍然最优先，且视为**显式指定**——不创建、不迁移。

### 2. 首次启动落地配置

按顺序：目标位置已有 → 直接用；否则从旧位置（工作目录、可执行文件真实目录）
复制一份，源文件保留；都没有则写内置默认模板（带注释，1558 字节）。

迁移和新建都记日志，`/_panel/api/config` 的 `origin` 能查到这份配置是哪来的。

### 3. 界面改动自动落盘

可编辑字段：规则开关/参数、日志级别、上游地址。改完直接写回 `config.toml`：
用 `toml_edit` 保留注释与段落顺序，写前备份 `.bak`。写盘失败不影响内存生效，
返回值带 `persisted=false` 与原因，界面明确提示「已生效但未写入配置」，不假装成功。

上游地址在内存里是独立的一份可变值，改完**下一个请求就生效**，不需要重启；
监听地址仍需手改文件重启（端口要重新绑定）。

规则页不再有「保存/放弃」，只保留「从文件重读」（用于手工改配置后同步）。

首次生成默认配置时（`origin = created`），启动日志打一条 WARN，
设置页顶部提示「当前是默认上游，请确认」，用户保存一次后不再显示。

### 4. 日志按本地日期切分

自己实现 appender：每次写入前比对 `Local::now()` 的日期，变了就切文件；
切换时按文件名排序清理，只保留最近 `retain_days` 个，只删匹配 `gateway.YYYY-MM-DD.log` 的文件，
目录里的其他内容一概不碰。

**验收标准（写死）**：文件内每一行的本地日期必须等于文件名日期。
单测用注入时钟覆盖跨天切换、同日重启追加、超量清理三种情况。

**为什么不继续用 `tracing_appender`**：它的 DAILY 是 UTC 且无法配置时区，
而日志行时间戳用的是本地时间，两套时区必然对不上。

**代价**：`log.dir` 为空不再表示「只输出终端」，而是平台默认目录；要改位置就填具体路径。
